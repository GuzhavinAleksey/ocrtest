# Финансовая отчётность: PDF → PNG → проверенные факты

Требуется **Node.js 24+** (используется встроенный SQLite), `npm ci` и доступный OpenAI-совместимый vLLM с vision-моделью. Реальный сервер в этой облачной среде недоступен: точность OCR здесь не измерена.

## Запуск

```bash
npm ci
# Только выбор страниц и PNG, без сервера модели:
npm run qwen -- report.pdf output --convert-only

# Распознавание, нормализация, проверки и импорт в локальную SQLite:
npm run qwen -- report.pdf output --config config/gazprom-2025.json --db output/financials.sqlite
```

`--db` необязателен. Для другого документа подготовьте отдельный JSON конфигурации. В окружении задайте `OPENAI_API_URL` (vLLM с `/v1`), `OPENAI_API_MODEL` и при необходимости `OPENAI_API_KEY`. Ключи не сохраняйте в Git.

В конфигурации явно задаются организация с постоянным ID, отчётный период, валюта ISO 4217, единица (`units`, `thousands`, `millions`), ожидаемые формы, профиль организации и его версия. Метаданные конфигурации должны быть сверены человеком с документом; модель не определяет юридическое лицо, валюту и масштаб автоматически. Пример `config/gazprom-2025.json` относится только к приложенному PDF. `gazprom` — внутренний ID примера, не ИНН.

Поддерживается календарная годовая отчётность по структуре форм **РСБУ 2025** (`ruleset: ras_2025`), ОКУД **0710001, 0710002, 0710004, 0710005**. Иные версии форм/промежуточные периоды требуют отдельного набора правил. Настройки примера нельзя без проверки переносить на другие годы и организации.

## Выбор страниц и полнота

Программа сначала читает текстовый слой всех страниц и ищет код формы с заголовком таблицы. В приложенном `report.pdf` это страницы PDF **11–19**, включая продолжения. Номера страниц не зашиты в алгоритм. Только эти страницы рендерятся и отправляются модели.

Независимо от модели составляется инвентарь кодов в геометрической колонке «Код показателя». Проверяются все строки этого инвентаря и все ожидаемые столбцы: три года баланса, два года результатов/потоков, семь компонентов капитала. Потерянные строки, ячейки, неподтверждённые строки и дубликаты блокируют автоматический импорт. Отсутствующая ожидаемая форма также ошибка.

`profile.expected_codes` задаёт полный список строк известного шаблона: он позволяет обнаружить потерянную страницу-продолжение. Для нового шаблона список нужно независимо сверить. Без него полнота подтверждается только относительно обнаруженных таблиц текстового слоя, а не всех возможных страниц документа.

Если колонка кодов не определяется однозначно, результат получает `needs_review`. PDF-сканы без текстового слоя требуют отдельного этапа OCR; программа не обещает автоматически распознавать их структуру. Повреждённый текстовый слой также требует проверки.

## Нормализованные данные

`output/financials.json` содержит исходные строки по страницам и `report`:

- `observations` — одна запись на ячейку: организация, форма, код, фиксированное английское `name`, отчётный период, период значения, дата моментного показателя, валюта, единица, множитель и компонент капитала;
- `provenance` каждой записи — SHA-256 PDF, страница, PNG, исходное название, точная запись ячейки и столбец, модель, версии программы/профиля и `run_id`;
- `issues`, `checks`, `status` — ошибки полноты/качества и результаты бухгалтерских сверок.

Пример ячейки (сокращён):

```json
{
  "organization_id": "gazprom",
  "form": "0710001",
  "code": "1100",
  "name": "non_current_assets",
  "report_period_start": "2025-01-01",
  "report_period_end": "2025-12-31",
  "period_start": null,
  "period_end": "2025-12-31",
  "indicator_date": "2025-12-31",
  "currency": "RUB",
  "unit": "thousands",
  "multiplier": 1000,
  "capital_component": null,
  "status": "reported",
  "value": 23339986338
}
```

Значения хранятся в единицах исходного документа. Прибыль на акцию сохраняется в `units`, независимо от масштаба основной таблицы. Для капитала даты и периоды выводятся из кода строки и отчётного года; семь компонентов получают фиксированные ключи `share_capital`, `treasury_shares`, `revaluation_surplus`, `additional_paid_in_capital`, `reserve_capital`, `retained_earnings`, `total`.

Статусы ячейки различаются:

| Статус | Значение |
| --- | --- |
| `reported` | Читаемое число, включая настоящий ноль |
| `dash` | Видимый прочерк, `value: null` |
| `not_applicable` | Явная отметка неприменимости, например X |
| `unreadable` | Пустая/нечитаемая ячейка, требует проверки |

`raw` сохраняет исходную запись. Число проверяется на соответствие `raw`; скобки означают минус, десятичная запятая нормализуется. Нечитаемое значение не подменяется нулём. Программа не использует угадывание чисел из произвольного ответа модели.

## Названия и профили

Базовый словарь — `src/indicator-names.ts`. Детализирующие коды могут иметь разный смысл у разных организаций. Их названия задаются в `profile.indicator_names` ключами `форма:код`, например `0710002:2111`. Неизвестный код/детализация без сопоставления блокирует импорт; универсального перевода по одному номеру не предполагается. Пример содержит расшифровки из приложенного отчёта. Изменение семантики требует новой версии профиля. Английские ключи — соглашение проекта, не официальный английский стандарт ОКУД.

## Контрольные соотношения

Проверяются суммы разделов баланса, актив = пассив, формирование прибыли и налога, поступления/платежи/сальдо трёх видов денежных потоков, изменение и конечный остаток денег, сумма семи компонентов и движение капитала. Межформенные сверки сопоставляют деньги и капитал с балансом.

Результаты правил: `passed`, `failed`, `uncheckable`. Пропущенные/нечитаемые ячейки не позволяют объявить сверку успешной. По умолчанию прочерк также не считается нулём. Если правила конкретного документа позволяют такое толкование, явно задайте `dash_is_zero: true` в его конфигурации. Это влияет только на арифметические проверки: исходные `status: dash` и `value: null` сохраняются. `tolerance` задаёт допустимое абсолютное расхождение в единицах документа; в примере 0. Скрытого округления/подгонки нет.

При любой ошибке или невозможности обязательной сверки результат — **`needs_review`**, код завершения CLI **2**. Проверенный результат — **`ready`**, код **0**. Ошибка чтения/сети/формата ответа — код **1**. `ready` означает прохождение реализованных проверок, а не гарантию правильности каждой ячейки: согласованная ошибка OCR может пройти арифметику.

## Хранение и повторный импорт

PNG сохраняются в `output/artifacts/<sha256 PDF>/2.0.0/`; существующие несовпадающие артефакты не перезаписываются. Итоговый JSON записывается атомарно после обработки всех страниц. Путь к PDF остаётся во внешнем `source`; оригинал PDF нужно хранить вместе с артефактами.

В SQLite создаются `documents`, `runs`, `facts`. Все результаты, включая сомнительные, сохраняются в `runs` с полным JSON; **только `ready` попадает в `facts`**. Импорт транзакционный. Для анализа основные измерения, значения и происхождение доступны отдельными SQL-столбцами.

`run_id` зависит от хеша PDF, конфигурации, модели и версии программы; ID факта дополнительно включает его измерения. Повтор идентичного результата не создаёт дубликатов. Если при том же `run_id` модель выдаёт другой результат, импорт отклоняется без перезаписи. Для намеренного переизвлечения измените версию профиля/обработки и проверьте новый результат. Весам модели под тем же именем нельзя приписывать неизменность: при замене весов также меняйте версию профиля обработки.

Разные документы/версии распознавания сохраняются отдельно. `logical_key` связывает один бизнес-факт внутри выбранного отчётного контекста. **Запросы должны выбирать конкретный `run_id`**, иначе сравнительные показатели/редакции можно просуммировать дважды. Автоматического выбора «последней правильной редакции» нет.

```sql
SELECT code, name, period_end, value, unit, status
FROM facts
WHERE run_id = :approved_run AND organization_id = :organization
ORDER BY form, code, period_end;
```

`value` — SQLite REAL; исходная запись сохранена в `raw_cell`. Для расчётов с обязательной десятичной точностью используйте decimal-арифметику по исходным значениям, а не бинарные float-суммы SQL.

## Проверки и измерение OCR

```bash
npm test
npm run typecheck
npm run evaluate -- predictions.json reference.json
```

Оценщик принимает массивы нормализованных ячеек либо `financials.json`. Эталон должен быть независимо размечен человеком. Он измеряет долю полностью правильных ячеек (статус + значение), точность числовых значений, пропуски, лишние ячейки и precision. Пустые эталоны и дубли измерений отклоняются. При расхождениях код завершения 2.

Тесты используют реальный приложенный PDF для выбора и PNG-рендера, подменённый API для полного конвейера и **два синтетических отчёта** с разными организациями, годами, единицами и размещением таблиц. Они проверяют полноту, соотношения, периоды, профили, статусы, SQLite и идемпотентность. Они **не измеряют точность реальной vision-модели**. Для этого нужны доступный vLLM и набор реальных отчётов разных организаций с ручной разметкой; в текущей среде их нет.

Сборка и запуск без ts-node:

```bash
npm run build
npm start -- report.pdf output --config config/gazprom-2025.json --db output/financials.sqlite
```

`tsconfig.pipeline.json` собирает новый конвейер. Старый экспериментальный `src/ocr.ts` с отсутствующим `ocr_type` остаётся вне этой сборки.
